# 개발 흐름: 기획부터 개발까지

새 프로젝트를 시작할 때 이 파일을 Claude에게 주고 "이 흐름으로 진행해줘"라고 하면 된다. 채용공고 수집·매칭 앱을 만들면서 실제로 거친 순서와, 그 과정에서 효과가 있었던 규칙을 정리했다. 예시는 그 프로젝트에서 가져왔다.

## 한눈에 보기

| 단계 | 하는 일 | 끝나면 남는 것 |
| --- | --- | --- |
| 1. 목표 잡기 | 무엇을, 누구를 위해, 어디까지 할지 대화로 정한다 | 목표와 범위 몇 줄 |
| 2. 가능성 검증 | 데이터와 외부 서비스를 직접 호출해 되는지 본다 | 비교 표와 추천안 |
| 3. 기획 문서 | 흐름, 결정, 운영 환경, 개발 순서를 공유 문서에 쓴다 | 기획 문서 |
| 4. 화면 구성 | 색 없이 정보 배치만 그린다 | 화면 목록과 와이어프레임 |
| 5. UX 검토 | 가독성과 군더더기를 점검하고 원칙으로 굳힌다 | 화면 원칙 |
| 6. 내용 상세 | 영역별로 무엇을 담을지 항목 수준까지 정한다 | 항목 표 |
| 7. 형식 원칙 | 어디를 고정하고 어디를 열어둘지 정한다 | 콘텐츠 형식 원칙 |
| 8. 개발 기반 | CLAUDE.md, 용어집, 데이터 형식, 기준 샘플을 만든다 | 레포의 기준 파일 |
| 9. 단계별 개발 | 데이터가 쌓여야 하는 것부터 만들고, 실제 데이터로 다듬는다 | 단계마다 볼 수 있는 결과 |

디자인 스타일(색·글꼴)은 4단계에서 후보만 좁히고, 9단계에서 실제 데이터를 넣어 보며 확정한다.

## 단계별로 할 일

### 1. 목표 잡기
- 사용자가 하고 싶은 것을 그대로 받아 큰 흐름(예: 수집 → 정리 → 리서치 → 매칭 → 보고)으로 나눈다.
- 질문은 번호를 붙여 한 번에 묻는다. 상세는 묻지 않는다. 기획은 큰 그림만, 상세는 개발하면서 정한다.
- 운영 조건을 일찍 확인한다: 비용(무료 우선인지), 어디서 돌릴지(클라우드, PC), 누가 쓸지(혼자, 지인).

예: "이직 준비용으로 경력 공고를 모아 회사 리서치와 매칭을 해서 보고받고 싶다" → 수집, 정리, 1차 필터, 회사 리서치, 매칭, 보고 6갈래로 나눔.

### 2. 가능성 검증
- 말로 추정하지 말고 실제로 호출해 본다. 데이터 소스, API, 사이트를 직접 조회해 양, 품질, 제약을 숫자로 확인한다.
- 후보를 비교 표로 정리하고 하나를 추천한다. 표의 열은 사용자의 목적에서 가져온다(예: 공고 수, 대기업 비율, 헤드헌터 공고, 본문 제공 여부).
- 막히면 원인을 구분한다: 우리 환경의 제약인지, 상대가 막는 것인지. 환경 문제면 사용자에게 고칠 방법을 알려준다.
- 검증 중에 발견한 제약은 기획에 바로 반영한다.

예: 직행·사람인·리멤버를 직접 조회 → "직행 기반 + 사람인·리멤버 보강"으로 결정. 지난 공고는 소급할 수 없다는 걸 발견 → 추이 데이터를 위해 수집을 먼저 시작하기로 함.

### 3. 기획 문서
- 사용자와 함께 보고 고칠 수 있는 공유 문서에 쓴다. 채팅에만 남기지 않는다.
- 담을 것: 전체 흐름 다이어그램, 영역별 결정, 운영 환경과 비용, 설정을 바꿨을 때 적용 방식, 개발 순서(단계마다 "끝나면 볼 수 있는 것"), 개발하며 정할 것(체크리스트), 출처.
- 결정이 나오면 그때그때 반영한다. 미정은 "개발하며 정할 것"에 넣고 넘어간다.

### 4. 화면 구성
- 스타일보다 구성을 먼저 확정한다. 구성 없이 스타일을 고르면 판단 기준이 없어 결정이 안 된다.
- 순서: 화면 목록과 이동 구조 → 화면마다 "이 화면이 답하는 질문"과 정보 순서 → 색 없는 와이어프레임.
- 디자인 캔버스에 화면을 보드로 나란히 올리고, 토글처럼 동작이 중요한 곳은 직접 눌러볼 수 있게 만든다.
- 스타일 탐색은 따로 빠르게 한다: 사용자가 좋아하는 서비스 스크린샷을 받아 같은 화면에 입혀 본 시안 여러 개 → 후보 2~3개로 좁히기.

### 5. UX 검토
화면을 다 그린 뒤 한 번에 점검하고, 결과를 화면 원칙으로 굳혀 모든 화면에 적용한다.

- 화면 목적에 맞는 것이 가장 먼저, 가장 크게 보이는가
- 빼도 되는 요소가 있는가(설명 문장, 범례, 중복 정보)
- 사용법이 모호한 UI가 있는가(무엇을 눌러야 할지, 무슨 뜻인지)
- 글자 크기, 굵기, 줄바꿈이 일정한가
- 문장이 너무 많지 않은가

예: 글자 크기 6단계, 굵기 3단계, 설명 문장 대신 ? 아이콘, 목록 한 항목 최대 4줄, 출처는 기본 숨김, 예외만 배지.

### 6. 내용 상세
- 영역마다 "무엇을 담을지"를 항목 목록 수준까지 정해서 표로 보여준다. 사용자가 보고 다듬는다.
- 각 항목에 데이터를 어디서 얻는지, 비용이 드는지를 같이 적는다. 비용이 없는 것과 드는 것을 나누면 기본/심층 같은 구분이 자연스럽게 나온다.
- 문장 길이, 분량, 계산법처럼 실제 데이터가 있어야 정할 수 있는 것은 "실제 데이터로 정할 것" 목록으로 미룬다.

### 7. 형식 원칙
형식을 너무 조이면 정보를 놓치고, 너무 풀면 화면과 문장이 매번 달라진다. 그래서 세 층으로 나눠 정한다.

| 층 | 무엇 | 강도 |
| --- | --- | --- |
| 그릇 | 화면 블록 모양 | 항상 고정 |
| 칸 | 담을 항목 | 영역마다 다름 |
| 문장 | 실제 글 | 길이와 규칙만 고정 |

- 블록 종류를 몇 개로 제한하고(예: 숫자 카드, 라벨-값, 표, 사실 목록, 단계, 인용, 칩), 모든 정보를 그중 하나로 그린다.
- 시간이 지나도 비교해야 하는 기준(분류, 점수, 계산법)은 고정하고 버전으로 관리한다.
- 필수 칸은 데이터가 늘 있는 곳에만 둔다. 나머지는 "찾아볼 주제"로 주고, 못 찾으면 "찾지 못함"으로 남긴다. 주제 밖 중요한 정보용 "기타" 칸을 둔다.
- 자유 형식에 같은 정보가 자주 나오면 고정 칸으로 올리고, 고정 칸이 자주 비면 주제로 내린다.

### 8. 개발 기반
개발은 여러 세션과 PC를 오가며 하므로, 기준을 레포 안에 파일로 둔다.

- `CLAUDE.md`: 프로젝트 설명, 기획 문서·디자인 링크, 개발 순서와 현재 단계, 운영 환경, 검증에서 확인된 사실, 내용·형식·화면 원칙
- `docs/glossary.md`: 화면 용어, 쓰지 않는 말, 표기 형식(날짜, 숫자, 증감), 버튼 문구
- 데이터 형식: AI 결과를 받을 JSON 형식과 검증 규칙
- 기준 샘플: 대표 입력 5~10개를 고정해 두고, 지시문이나 형식을 바꿀 때마다 전후를 비교한다

### 9. 단계별 개발
- 시간이 지나야 쌓이는 데이터(예: 추이)가 있으면 그것부터 만든다.
- 단계마다 "끝나면 볼 수 있는 결과"를 정하고, 그 결과를 사용자에게 보여주며 넘어간다.
- 실제 데이터가 들어오면 미뤄둔 "실제 데이터로 정할 것"을 하나씩 정한다. 디자인 스타일도 이때 실제 화면으로 확정한다.

## 진행 규칙

1. **먼저 만들어 보여준다.** 빈 질문보다 시안, 표, 추천안을 내고 반응을 받는다.
2. **선택지는 2~4개와 추천을 함께 낸다.** 정할 수 있는 것은 정하고 알린다.
3. **결정은 바로 문서에 남긴다.** 미정은 목록으로 남기고 다음으로 넘어간다.
4. **사실과 추정을 구분한다.** 검증 결과는 숫자와 출처로 말한다.
5. **피드백은 원칙으로 넓힌다.** 한 화면에서 나온 지적(예: "출처는 필요할 때만")은 모든 화면에 같은 원칙으로 적용한다.
6. **상세는 실제 데이터로 정한다.** 화면은 와이어프레임까지, 분량과 문장 길이는 데이터를 보고 정한다.
7. **매 라운드 끝에 짧게 보고한다.** 바뀐 것, 결정이 필요한 것, 다음 제안 순서로.
8. **운영은 무료와 클라우드를 우선한다.** 외부 서비스(AI 모델 등)는 바꿔 끼울 수 있게 만든다.

## 하지 말 것

- 화면 구성 전에 색·글꼴 스타일부터 고르기
- 화면에 설명 문장을 늘어놓기
- 처음부터 모든 내용을 칸으로 꽉 조이거나, 반대로 완전히 자유롭게 두기
- 실제 데이터 없이 분량과 문장 길이를 확정하기
- 결정을 채팅에만 남기기
