# 기준 목록(텍소노미)

공고·회사·프로필을 나누는 고정 목록과, 그 목록을 코드로 관리하는 규칙. 실제 값은 `config/taxonomy/`, 읽기와 검사는 `src/jobpost/taxonomy.py` 한 곳.

## 목록

| 목록 | 파일 | 코드 | 상위를 코드에 넣나 | 상태 |
| --- | --- | --- | --- | --- |
| 직무 분야 | `jobs.yaml` fields | JF + 2자리 (JF01 AI·데이터) | – | 21개(AI·데이터 + 다른 분야 20). AI·데이터 밖은 공고 분류와 업무 꼬리표에 분야 그대로 쓴다 |
| 직무 유형 | `jobs.yaml` types | JT + 3자리 (JT001 데이터 엔지니어) | 아니오. 분야는 `field` 칸 | AI·데이터만 13개. 다른 분야는 지인을 받기 전에 나눈다 |

## 코드 규칙

- 코드는 한 번 쓰면 다시 쓰지 않고, 번호를 다시 매기지 않는다. 이름·설명은 고쳐도 된다(설명이 AI 지시문에 들어가는 목록은 그 목록의 `version`을 올린다).
- **상위를 코드에 넣는 기준**: 상위가 하나뿐이고, 거의 안 바뀌고, 판정에 상위를 쓸 때만. 셋 중 하나라도 아니면 코드는 일련번호로 두고 상위는 칸에 적는다.
  - 업종은 판정에 상위를 쓴다(같은 중분류 충족, 같은 대분류 일부) → 코드에 넣는다.
  - 직무 유형은 분야를 옮길 수 있다(기획·PM이 데이터 쪽과 일반 기획 사이) → 넣지 않는다.
  - 스킬은 묶음이 여럿일 수 있고(Databricks: 데이터 처리이자 저장) 묶음은 보기용이다 → 넣지 않는다.
- **갈라지거나 없앨 때**: 지우지 않고 `retired: 날짜`와 `replaced_by: [새 코드]`를 남긴다. 지난 데이터는 옛 코드로 읽어도 새 코드로 이어 셀 수 있다.
- **화면**: 이름만 보인다. 코드는 내부용.
- **검사**: `taxonomy.validate()`(테스트에서 돈다): 코드 형식·중복, 없는 분야·묶음·스킬, 업종 중분류가 대분류로 시작하는지, `replaced_by`가 있는 코드인지, 지난 id(직무·업종)가 겹치는지. 프로필 직무의 code가 있는 코드인지는 테스트(test_profile_role_codes_exist)가 본다.
- **직무 유형을 은퇴시킬 때**: 저장된 지난 id가 이름을 잃지 않게 `legacy_aliases`에 '옛 id → 이어받는 id'를 함께 적는다. 다른 분야 소속 직무 유형은 분야 칸(field)으로 계열이 정해진다(AI·데이터 밖이면 그 밖 계열).

## 업종

- **시장(도메인) 기준**: 회사가 일하는 시장으로 나눈다. KSIC(법정 사업)는 IT 회사를 하는 일과 상관없이 58·62·63으로 묶어서(공고 회사의 DART 업종 중 50%), 업종 자체가 아니라 근거의 하나로 쓴다.
- **회사 업종 정하는 순서**: 예외(이유·그때 DART 값) → 공공기관 목록 → KSIC 대응표(`ksic`, 긴 앞자리 먼저, `taxonomy.industry_from_ksic`) → 공고 정리의 회사 도메인(AI, 공용, 회사별 다수결) → 확인 안 됨. KSIC가 `ksic_generic`(소프트웨어·SI·정보서비스·연구개발·기술서비스·지주회사)이거나 DART에 없는 회사는 AI로 간다(2026-11-04 공고의 약 75%). DART 코드가 대응표 앞자리보다 짧아 여러 업종에 걸치면(예: 649는 기타 금융과 지주회사) 정하지 않고 같은 길로 보낸다.
- **2026-11-04 대조**: KSIC 11차(한국무역보험공사 업종코드 파일, 공공데이터포털 15064297)와 데이터·AI 공고 3,736건(헤드헌팅 제외) 회사의 DART 업종. DART 업종이 있는 공고 1,887건 중 대응표로 정해진 공고 950건, 도메인을 모르는 코드 934건, 대응표에 없는 코드 0건. 지난 23개에서 빠졌던 광고·마케팅, 인력·아웃소싱, 기계·로봇·장비, 회계·법률·컨설팅, 보안, 모빌리티 서비스, 에너지를 더했고, 겹치던 IT 플랫폼·SI·핀테크·이커머스와 자동차 제조·모빌리티를 나눴다.

- **업종 경험(공고 정리 v5)**: 업종 경험 문장은 AI(그대로 옮김)와 코드(업종 사전 말과 경험·이해 같은 말이 함께 있는 줄)가 함께 찾고, 나머지는 코드가 정한다. 업종은 맞출 사전(`industries.yaml` words, 대분류 words는 넓은 말: 금융·제조·공공), 필수·우대는 문장이 놓인 본문 제목(업무 아래면 버림). 관심만 묻는 문장은 버린다. 대분류는 같은 필수/우대일 때만 그 아래 중분류를 덮는다(금융 필수 + 보험 우대는 둘 다). 사전에 걸리지 않은 문장은 domain_unmatched로 남겨 월간 점검에서 단어를 더한다. 사전은 AI 없이 다시 계산할 수 있다. 판정: 요구가 대분류면 그 아래 경력 아무거나 충족, 중분류면 같은 중분류 충족 · 같은 대분류 일부(`taxonomy.industry_fit`).
- **회사 도메인(공고 정리 v3)**: 회사가 일하는 시장. 회사 업종 정하는 순서의 다수결에 쓰고, 헤드헌팅 공고는 회사 다수결에서 빼고 그 공고의 업종으로만 쓴다.

## 스킬 관계

판정에 쓰는 관계는 셋뿐이고 모두 코드끼리 잇는다. 묶음(SG)은 판정에 쓰지 않는다.

| 관계 | 칸 | 예 | 판정 |
| --- | --- | --- | --- |
| 별칭 | `aliases` | Apache Spark, PySpark → Spark(SK) | 같은 스킬 |
| 바꿔 쓰는 묶음 | `interchangeable` (IS) | PostgreSQL · MySQL · Oracle | 서로 충족 |
| 넓은 개념 | `broader` | vLLM → LLM 서빙 | 공고가 넓은 개념이면 좁은 쪽이 충족, 반대는 일부 |

스킬이 아닌 말(AI, 클라우드, 데이터 분석 등)은 `stopwords`에 둔다. 넓은 개념(`broader`)과 제외어는 D 점검에서 채운다(2026-11-03 지금은 비어 있음).

## 예외(기업 구분 · 회사 업종)

공적 근거로 정하지 못하거나 틀리게 정해지는 회사는 사람이 확인해 예외로 둔다(`config/company_class.yaml`).

| 칸 | 값 |
| --- | --- |
| 이유 | EX01 DART 없음 / EX02 DART 틀림 / EX03 기타(설명 필수) |
| 근거 | 출처와 숫자 |
| 그때 DART 값 | 예외를 만들 때 본 DART 값(없으면 비움) |
| 확인한 날 | 날짜 |

예외 칸 중 reason·dart_value는 2026-11-03 적었고, 월간 점검의 비교는 회사 업종 배정을 구현할 때 함께 만든다(예정). 월간 점검 보고에서: DART 값이 예외와 같아지면 "예외 필요 없음, 지워도 됨", DART 값이 새로 생겼거나 바뀌었는데 예외와 다르면 둘 다 보여 주고 어느 쪽을 쓸지 묻는다(답을 받기 전에는 예외를 쓴다). EX01은 DART 값이 생기는 순간 점검 대상에 오르고, EX02는 유지한다.

## 정기 점검

매월 26일 '기업 구분·업종 점검 보고'(예약 작업)에서 본다. 고치지 않고 선택지와 추천만 보고한다.
- 업종: 공고 회사의 KSIC 코드 중 대응표에 없는 코드, 대응표로 정한 업종과 공고 정리(AI)의 회사 도메인이 다른 회사, 업종별 공고 분포와 기타·확인 안 됨 비율, 한 업종이 내 분야 공고의 15%를 넘으면 갈라 볼지
- 예외: DART 값과 비교(위 '예외')
- 스킬: 사전에 없는 새 이름(D 이후)
- 업종 경험: 업종 사전에 걸리지 않은 문장(domain_unmatched) 중 반복되는 말 → words에 더할지

## 코드로 옮기기(진행 중)

지금 데이터(data 브랜치 `state.jsonl`·`facts.jsonl`, Supabase 설정·프로필·매칭)는 지난 id(`data_eng`, `bank`)로 저장돼 있다. 옮기기 전까지 다른 모듈은 `config.load("job_types"·"skills"·"profile"·"match_guide")`로 예전 모양의 보기를 받고, 보기는 `taxonomy.py`가 만든다. 항목마다 `legacy` 칸이 지난 id → 코드 대응표다(`taxonomy.code_of`).

순서(docs/decisions.md 2026-11-03): A 코드 체계 → B 업종 대조·확정 → C 업종 경험 지시문 → D 스킬 사전 점검 → 구현 → 데이터 옮기기(백업 먼저).
